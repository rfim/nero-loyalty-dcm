# DCM definitions

One folder per `NERO_DB` schema it manages, mirroring the schema structure
so it's obvious at a glance what DCM owns and where. Generated by
`ingestion/build.py` from `ingestion/contract/` (meta.yaml + datasets/*.yaml)
-- do not hand-edit any `.sql` file under here; edit the contract and rerun
`python ingestion/build.py` instead.

```
00_staging/        typed, unvalidated landing -- STAGING_<DATASET> tables +
                    STAGING_BATCH_MANIFESTS + LANDING_STAGE (raw.sql)
03_lineage/         pipeline stage/dependency documentation -- schema only,
                    rows loaded by `ingestion/build.py --seed` (lineage.sql)
05_pii_control/     PII column registry -- schema only, rows loaded by
                    `ingestion/build.py --seed` (pii_registry.sql)
```

## What's deliberately NOT here

- **`01_BRONZE`** -- dbt-owned, not DCM-managed. Built by
  `analytics/models/bronze/bronze_<dataset>.sql`, which reads directly from
  `00_staging`'s typed tables and filters by the contract's rules in plain
  SQL. Used to be generated here too (as `validated.sql`, defining
  `VALIDATED_<DATASET>` under the pre-rename `01_SILVER` schema) until the
  PROCESS_BATCH retirement moved ownership to dbt.
- **`02_CONTROL`** -- plain SQL via `account_setup/control_metadata_rework.sql`,
  not DCM. Used to hold the whole hand-written contract-validation control
  plane (`CONTROL_DATA_CONTRACTS`, `CONTROL_RUN_AUDIT`, `CONTROL_RELEASE_POINTER`,
  `PROCESS_BATCH`/`RUN_PENDING`) -- all retired when dbt replaced it. Now
  holds `CONTRACT_REJECTIONS`, a live view.
- **`04_METADATA`** -- plain SQL via `account_setup/control_metadata_rework.sql`
  and `account_setup/dbt_pipeline_metadata.sql`, not DCM. Holds
  `DATASET_FRESHNESS` (live view), `PIPELINE_WATERMARKS` and
  `PIPELINE_RUN_LOG` (tables, written by dbt's on-run-end hooks --
  see `analytics/macros/log_pipeline_run.sql`).

The dividing line: DCM manages schema/table *structure* for the ingestion
entry point (what lands, and the fixed lineage/PII metadata describing it).
Everything downstream of landing -- contract filtering, transforms, run
telemetry -- is dbt's job (schema) or a plain idempotent SQL script's job
(schema + grants), not DCM's, because those change on a different cadence
and dbt/plain SQL already own their own deploy paths.

## Reference-only (not deployed by DCM at all)

`ingestion/reference/s3.sql` and `ingestion/reference/masking.sql` live
outside `sources/definitions/` on purpose -- both unverified (no live AWS
credentials; this account's edition lacks masking policy support) and not
meant to be deployed until someone validates them for real.
